# AI Config

Modular, agent-harness-agnostic AI configuration. Canonical content is pure
prompt — each harness differs only by a thin entry file and generated stubs.

## Structure

```
core/           Routing policy + engineering principles. Harness-agnostic.
skills/         Canonical skills (name/description frontmatter + pure prompt).
agents/         Canonical agent bodies (pure prompts — NO frontmatter).
adapters/       Harness entry files ONLY (AGENTS.md, GEMINI.md, configs).
knowledge/      Per-project persistent knowledge base. Portable across tools.
scripts/        sync.sh — pointer-stub generator.
```

## Canonical vs Generated

- `agents/<name>.md` are pure bodies with no frontmatter. Per-harness
  frontmatter (description, mode, permissions, tools, model) is defined in
  `scripts/sync.sh`.
- `scripts/sync.sh` generates **pointer stubs** into machine config — never
  inline canonical content:
  - `~/.config/opencode/agent/<name>.md`
  - `~/.gemini/config/agents/<name>.md`
- antigravity rules are wired via absolute-path `@` mentions in
  `adapters/antigravity/GEMINI.md` — no rule stubs needed.
- **Failure-mode note**: subagent stubs are pointers — the subagent MUST read
  its canonical file before acting.
- Run `scripts/sync.sh` only when adding, removing, or renaming an agent.
  Editing a canonical body needs no re-sync. The script is
  idempotent and removes stale stubs whose canonical file no longer exists.

## Adapters

Adapters contain harness entry files only — tool glossaries, invocation
syntax, and harness behavior notes.

| Adapter | Entry file | Machine config wiring | Status |
|---|---|---|---|
| `opencode` | `adapters/opencode/AGENTS.md` | `~/.config/opencode/{AGENTS.md,opencode.jsonc,plugin}` symlinked into the repo; `~/.config/opencode/agent/` generated by `sync.sh` | ✅ Active |
| `antigravity` | `adapters/antigravity/GEMINI.md` | `~/.gemini/GEMINI.md` symlinked into the repo; `~/.gemini/config/` is a real dir with generated `agents/`, symlinked `hooks/` + `hooks.json`, and a real `config.json` | ✅ Active |

## Updating Content

- **Edit a rule**: change `core/<file>.md` directly. opencode globs
  `ai/core/*.md` via `instructions`; antigravity loads it via the `@`
  mention in `adapters/antigravity/GEMINI.md`.
- **Add / remove a core rule**: edit `core/` and update the `@` mention list
  in `adapters/antigravity/GEMINI.md` accordingly.
- **Edit an agent**: change `agents/<name>.md` directly — stubs are pointers.
- **Add / rename an agent**: write the pure body to `agents/<name>.md`, add
  its description + per-harness frontmatter in `scripts/sync.sh`, run
  `scripts/sync.sh`, then restart the harnesses.

## Knowledge Base

`knowledge/` is tool-agnostic.

```
knowledge/
├── _index.md               — project registry (entry context)
├── _template/              — scaffolding templates
├── _shared/dependencies/   — shared registry, one file per dependency
└── <project-name>/         — per-project knowledge files
    ├── architecture.md
    ├── adr.md
    ├── vocabulary.md
    ├── gotchas.md
    └── wip.md
```

Per-project files (`architecture.md`, `adr.md`, `vocabulary.md`, `gotchas.md`, `wip.md`) stay isolated. Cross-project dependency knowledge lives in `_shared/dependencies/` — one markdown file per library, with a table of all projects that use it.
