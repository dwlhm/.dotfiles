# AI Config

Modular, agent-harness-agnostic AI configuration. Canonical content is pure
prompt — each harness differs only by a thin entry file and generated stubs.

## Structure

```
core/           Routing policy + engineering principles. Harness-agnostic.
skills/         Canonical skills (second-brain, subagent-management, ui-contrast, ui-ux-interaction-reasoning; name/description frontmatter + pure prompt).
agents/         Canonical agent bodies (pure prompts — NO frontmatter).
adapters/       Harness entry files ONLY (AGENTS.md, GEMINI.md, configs).
extensions/     pi subagent tool mechanism (symlinked into ~/.pi/agent/extensions/).
knowledge/      Per-project persistent knowledge base. Portable across tools.
scripts/        sync.sh — agent stub generator; sync-codex.sh — Codex links.
```

## Canonical vs Generated

- `agents/<name>.md` are pure bodies with no frontmatter. Per-harness
  frontmatter (description, mode, permissions, tools, model) is defined in
  `scripts/sync.sh`.
- `scripts/sync.sh` generates **inlined stubs** into machine config — inlining
  canonical agent bodies directly beneath harness frontmatter for zero-latency
  execution (eliminates initial `view_file` startup tool calls):
  - `~/.config/opencode/agent/<name>.md`
  - `~/.gemini/config/agents/<name>.md`
  - `~/.pi/agent/agents/<name>.md` (discovered by the subagent extension on
    every tool invocation)
- antigravity rules are inlined into `adapters/antigravity/GEMINI.md` by
  `scripts/sync.sh` — the file is generated, not hand-edited.
- Codex reads canonical role bodies at dispatch through explicit subagent
  instructions in `adapters/codex/AGENTS.md`; `sync.sh` does not generate
  Codex agents or register them in `config.toml`.
- Run `scripts/sync.sh` whenever adding, removing, renaming, or editing an agent
  so machine stubs stay synchronized. The script is idempotent and removes stale
  stubs whose canonical file no longer exists.

## Adapters

Adapters contain harness entry files only — tool glossaries, invocation
syntax, and harness behavior notes.

| `opencode` | `adapters/opencode/AGENTS.md` | `~/.config/opencode/{AGENTS.md,opencode.jsonc,plugin}` symlinked into the repo; `~/.config/opencode/agent/` generated by `sync.sh` | ✅ Active |
| `antigravity` | `adapters/antigravity/GEMINI.md` | `~/.gemini/GEMINI.md` symlinked into the repo; `~/.gemini/config/` is a real dir with generated `agents/`, symlinked `hooks/` + `hooks.json`, and a real `config.json` | ✅ Active |

## Codex Setup

```sh
bash ~/.dotfiles/ai/scripts/sync-codex.sh
```

The standalone installer derives source paths from its repository location,
honors `HOME` and `CODEX_HOME`, and preserves conflicting files, directories,
or symlinks in adjacent timestamped, uniquely named backup directories
(`original` contains the preserved entry). A nonempty `AGENTS.override.md`
blocks installation because it would shadow the adapter. Existing links to
the correct source are left alone. Reruns add or update links only; they do
not remove links for deleted skills. Other harnesses and `config.toml` are
unaffected. The adapter's canonical paths assume the repository is at
`~/.dotfiles`; temporary `HOME` overrides are useful for installer tests.

Start a new Codex desktop task after installation to load the entry point and
all canonical core rules. Agent bodies are read on the next dispatch. Rerun
the installer after adding or renaming skills. Filesystem wiring can be
verified independently of the CLI: the current local `codex --help` fails
with `ENOENT` for the native binary in the npm `@openai/codex` installation;
repairing that separate CLI installation is outside this setup.

## Updating Content

- **Edit a rule**: change `core/<file>.md` directly. opencode globs
  `ai/core/*.md` via `instructions`; antigravity inlines it via
  `scripts/sync.sh` into `adapters/antigravity/GEMINI.md`; pi reads the core
  rules via the pointer table in `adapters/pi/AGENTS.md` at session start.
  Codex enumerates and reads every `ai/core/*.md` file at session start.
- **Add / remove a core rule**: edit `core/`, then update the inline list in
  `scripts/sync.sh` (antigravity) and the pointer tables in `adapters/pi/AGENTS.md`
  and `adapters/zed/AGENTS.md`, then run `scripts/sync.sh`.
- **Edit an agent**: change `agents/<name>.md`, then run `scripts/sync.sh` to
  propagate changes into machine config stubs.
- **Add / rename an agent**: write the pure body to `agents/<name>.md`, add
  its description + per-harness frontmatter in `scripts/sync.sh`, run
  `scripts/sync.sh`, then restart the harnesses.

## Knowledge Base

`knowledge/` is tool-agnostic.

```
knowledge/
├── _index.md               — project registry (entry context)
├── _template/              — scaffolding templates
├── _shared/dependencies/   — shared registry, one file per dependency
└── <project-name>/         — per-project knowledge files
    ├── architecture.md
    ├── adr.md
    ├── vocabulary.md
    ├── gotchas.md
    └── wip.md
```

Per-project files (`architecture.md`, `adr.md`, `vocabulary.md`, `gotchas.md`, `wip.md`) stay isolated. Cross-project dependency knowledge lives in `_shared/dependencies/` — one markdown file per library, with a table of all projects that use it.
